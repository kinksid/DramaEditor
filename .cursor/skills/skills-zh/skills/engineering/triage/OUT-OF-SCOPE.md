# 超出范围的知识库

仓库中的 `.out-of-scope/` 目录存储被拒绝功能请求的持久记录。它有两个目的：

1. **机构记忆**——为什么功能被拒绝，这样推理不会在 issue 关闭时丢失
2. **去重**——当新 issue 与先前拒绝匹配时，技能可以显示先前的决策而不是重新讨论它

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个文件。请求相同内容的多个 issue 分组在一个文件下。

## 文件格式

文件应该以轻松、可读的风格编写——更像简短的设计文档而不是数据库条目。使用段落、代码示例和示例使推理清晰并对首次遇到的人有用。

```markdown
# 深色模式

此项目不支持深色模式或面向用户的主题。

## 为什么这不在范围内

渲染管道假设在 `ThemeConfig` 中定义的单一调色板。支持多个主题需要：

- 包装整个组件树的主题上下文提供者
- 每个组件的主题感知样式解析
- 用户主题偏好的持久层

这是一个重大的架构更改，与项目专注于内容创作不符。主题是嵌入或重新分发输出的下游消费者的关注点。

```ts
// 当前的 ThemeConfig 接口不是为运行时切换设计的：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，在构建时解析
  fonts: FontStack;
}
```

## 先前的请求

- #42 — "添加深色模式支持"
- #87 — "用于可访问性的夜间主题"
- #134 — "深色主题选项"
```

### 命名文件

使用简短、描述性的 kebab-case 名称作为概念：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应该足够可识别，以便浏览目录的人在打开文件之前理解被拒绝的内容。

### 编写原因

原因应该是实质性的——不是"我们不想要这个"而是为什么。好的原因参考：

- 项目范围或哲学（"此项目专注于 X；主题是下游关注点"）
- 技术约束（"支持这需要 Y，这与我们的 Z 架构冲突"）
- 战略决策（"我们选择使用 A 而不是 B，因为……"）

原因应该是持久的。避免引用临时情况（"我们现在太忙了"）——那些不是真正的拒绝，它们是延期。

## 何时检查 `.out-of-scope/`

在分类期间（步骤 1：收集上下文），读取 `.out-of-scope/` 中的所有文件。评估新 issue 时：

- 检查请求是否匹配现有的超出范围概念
- 匹配是通过概念相似性，而不是关键字——"夜间主题"匹配 `dark-mode.md`
- 如果匹配，向维护者显示："这类似于 `.out-of-scope/dark-mode.md`——我们之前因为这个原因拒绝了它。你仍然感觉一样吗？"

维护者可能：

- **确认**——新 issue 添加到现有文件的"Prior requests"列表中，然后关闭
- **重新考虑**——超出范围文件被删除或更新，issue 通过正常分类进行
- **不同意**——issue 相关但不同，继续进行正常分类

## 何时写入 `.out-of-scope/`

仅当**增强**（不是 bug）被拒绝为 `wontfix` 时。流程：

1. 维护者决定功能请求超出范围
2. 检查匹配的 `.out-of-scope/` 文件是否已存在
3. 如果是：将新 issue 附加到"Prior requests"列表
4. 如果否：创建具有概念名称、决策、原因和第一个先前请求的新文件
5. 在 issue 上发布评论解释决策并提及 `.out-of-scope/` 文件
6. 使用 `wontfix` 标签关闭 issue

## 更新或删除超出范围文件

如果维护者改变对先前拒绝概念的想法：

- 删除 `.out-of-scope/` 文件
- 技能不需要重新开放旧 issue——它们是历史记录
- 触发重新考虑的新 issue 通过正常分类进行
