# 编写代理简报

代理简报是在 GitHub issue 移动到 `ready-for-agent` 时发布的结构化评论。它是 AFK 代理将使用的权威规范。原始 issue 正文和讨论是上下文——代理简报是契约。

## 原则

### 持久性优于精确性

issue 可能在 `ready-for-agent` 中停留数天或数周。在此期间代码库会发生变化。编写简报使其即使文件被重命名、移动或重构后仍然有用。

- **要**描述接口、类型和行为契约
- **要**命名代理应该查找或修改的特定类型、函数签名或配置形状
- **不要**引用文件路径——它们会过时
- **不要**引用行号
- **不要**假设当前实现结构将保持不变

### 行为性，而不是过程性

描述系统应该做**什么**，而不是**如何**实现它。代理将新鲜探索代码库并做出自己的实现决策。

- **好：** "`SkillConfig` 类型应该接受可选的 `schedule` 字段，类型为 `CronExpression`"
- **坏：** "打开 src/types/skill.ts 并在第 42 行添加 schedule 字段"
- **好：** "当用户运行不带参数的 `/triage` 时，他们应该看到需要注意的 issue 摘要"
- **坏：** "在主处理函数中添加 switch 语句"

### 完整的验收标准

代理需要知道何时完成。每个代理简报必须有具体、可测试的验收标准。每个标准都应该可以独立验证。

- **好：** "运行 `gh issue list --label needs-triage` 返回已经过初步分类的 issue"
- **坏：** "分类应该正常工作"

### 明确的范围边界

说明什么不在范围内。这防止代理过度装饰或对相邻功能做出假设。

## 模板

```markdown
## 代理简报

**类别：** bug / enhancement
**摘要：** 需要发生什么的一行描述

**当前行为：**
描述现在发生的事情。对于 bug，这是损坏的行为。
对于增强，这是功能构建的现状。

**期望行为：**
描述代理工作完成后应该发生什么。
具体说明边缘情况和错误条件。

**关键接口：**
- `TypeName`——需要什么变化以及为什么
- `functionName()` 返回类型——当前返回什么 vs 应该返回什么
- 配置形状——需要任何新的配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**超出范围：**
- 不应在此 issue 中更改或解决的事情
- 可能看起来相关但独立的相邻功能
```

## 示例

### 好的代理简报（bug）

```markdown
## 代理简报

**类别：** bug
**摘要：** 技能描述截断丢弃单词中间，产生损坏的输出

**当前行为：**
当技能描述超过 1024 个字符时，无论单词边界如何，它都会在正好
1024 个字符处截断。这产生的描述在单词中间结束（例如"Use when the user wants to confi"）。

**期望行为：**
截断应该在 1024 个字符之前的最后一个单词边界处中断
并附加"..."以指示截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段——不需要类型更改，
  但填充它的验证/处理逻辑需要尊重单词边界
- 任何读取 SKILL.md frontmatter 并提取描述的函数

**验收标准：**
- [ ] 1024 个字符以下的描述不变
- [ ] 超过 1024 个字符的描述在 1024 个字符之前的最后一个单词边界处截断
- [ ] 截断的描述以"..."结尾
- [ ] 包括"..."的总长度不超过 1024 个字符

**超出范围：**
- 更改 1024 个字符限制本身
- 多行描述支持
```

### 好的代理简报（增强）

```markdown
## 代理简报

**类别：** enhancement
**摘要：** 添加 `.out-of-scope/` 目录支持以跟踪被拒绝的功能请求

**当前行为：**
当功能请求被拒绝时，issue 以 `wontfix` 标签和评论关闭。没有持久的决策或推理记录。
未来类似的请求需要维护者回忆或搜索先前的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，这些文件捕获决策、推理和链接到所有请求该功能的 issue。在分类新 issue 时，应检查这些文件以匹配。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式——每个文件应该有
  `# Concept Name` 标题、`**Decision:**` 行、`**Reason:**` 行，
  和带有 issue 链接的 `**Prior requests:**` 列表
- 分类工作流程应尽早读取所有 `.out-of-scope/*.md` 文件
  并通过概念相似性将传入 issue 与它们匹配

**验收标准：**
- [ ] 将功能关闭为 wontfix 会在 `.out-of-scope/` 中创建/更新文件
- [ ] 文件包括决策、推理和指向关闭 issue 的链接
- [ ] 如果匹配的 `.out-of-scope/` 文件已存在，新 issue 会
      附加到其"Prior requests"列表而不是创建重复项
- [ ] 在分类期间，检查现有的 `.out-of-scope/` 文件并在
      新 issue 匹配先前拒绝时显示

**超出范围：**
- 自动匹配（人类确认匹配）
- 重新开放先前拒绝的功能
- bug 报告（只有增强拒绝进入 `.out-of-scope/`）
```

### 坏的代理简报

```markdown
## 代理简报

**摘要：** 修复分类 bug

**做什么：**
分类东西坏了。查看主文件并修复它。
大约第 150 行的函数有问题。

**要更改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这很糟糕，因为：
- 没有类别
- 模糊的描述（"分类东西坏了"）
- 引用将过时的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前与期望行为
