# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一两句话描述这个上下文是什么以及为什么存在。}

## 语言

**订单**：
{术语的简洁描述}
_避免_：购买、交易

**发票**：
交付后发送给客户的付款请求。
_避免_：账单、付款请求

**客户**：
下订单的个人或组织。
_避免_：客户端、买家、账户

## 关系

- **订单**产生一个或多个**发票**
- **发票**属于恰好一个**客户**

## 示例对话

> **开发者：** "当**客户**下**订单**时，我们是否立即创建**发票**？"
> **领域专家：** "不——只有在确认**履行**后才生成**发票**。"

## 已标记的歧义

- "account" 用于表示**客户**和**用户**——已解决：这些是不同的概念。
```

## 规则

- **要有主见。** 当多个词表示同一概念时，选择最好的一个，并将其他词列为要避免的别名。
- **明确标记冲突。** 如果术语使用模糊，在"已标记的歧义"中指出并给出明确的解决方案。
- **保持定义紧凑。** 最多一句话。定义它是什么，而不是它做什么。
- **显示关系。** 使用粗体术语名称，并在明显时表达基数。
- **仅包含特定于此项目上下文的术语。** 通用编程概念（超时、错误类型、实用模式）不属于此处，即使项目广泛使用它们。在添加术语之前，问：这是此上下文独有的概念，还是通用编程概念？只有前者属于此处。
- **当自然集群出现时将术语分组在子标题下。** 如果所有术语都属于单个凝聚区域，平面列表即可。
- **编写示例对话。** 开发者和领域专家之间的对话，展示术语如何自然交互并澄清相关概念之间的边界。

## 单上下文与多上下文仓库

**单上下文（大多数仓库）：** 仓库根目录下一个 `CONTEXT.md`。

**多上下文：** 仓库根目录下的 `CONTEXT-MAP.md` 列出上下文、它们的位置以及它们之间的关系：

```md
# 上下文映射

## 上下文

- [订购](./src/ordering/CONTEXT.md) — 接收和跟踪客户订单
- [计费](./src/billing/CONTEXT.md) — 生成发票和处理付款
- [履行](./src/fulfillment/CONTEXT.md) — 管理仓库拣货和发货

## 关系

- **订购 → 履行**：订购发出 `OrderPlaced` 事件；履行消费它们以开始拣货
- **履行 → 计费**：履行发出 `ShipmentDispatched` 事件；计费消费它们以生成发票
- **订购 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

技能推断适用哪种结构：

- 如果存在 `CONTEXT-MAP.md`，读取它以查找上下文
- 如果仅存在根 `CONTEXT.md`，则为单上下文
- 如果两者都不存在，则在解析第一个术语时惰性创建根 `CONTEXT.md`

当存在多个上下文时，推断当前主题与哪个上下文相关。如果不清楚，询问。
