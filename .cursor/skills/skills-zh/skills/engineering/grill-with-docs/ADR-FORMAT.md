# ADR 格式

ADR 位于 `docs/adr/` 中并使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

惰性创建 `docs/adr/` 目录——仅在需要第一个 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么，我们决定了什么，以及为什么。}
```

就是这样。ADR 可以是一个段落。价值在于记录*做出了*决策以及*为什么*——而不是填写部分。

## 可选部分

仅当它们增加真正价值时才包含这些。大多数 ADR 不需要它们。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——在重新审视决策时有用
- **考虑的选项**——仅当被拒绝的替代方案值得记住时
- **后果**——仅当需要指出非显而易见的下游影响时

## 编号

扫描 `docs/adr/` 以查找最高的现有编号并加一。

## 何时提供 ADR

以下三个条件必须都为真：

1. **难以逆转**——稍后改变主意的成本是有意义的
2. **没有上下文时令人惊讶**——未来的读者会查看代码并想知道"他们到底为什么这样做？"
3. **真正权衡的结果**——存在真正的替代方案，你出于特定原因选择了一个

如果决策容易逆转，跳过它——你只会逆转它。如果不令人惊讶，没有人会想知道为什么。如果没有真正的替代方案，除了"我们做了显而易见的事情"之外没有什么可记录的。

### 什么符合条件

- **架构形状。** "我们正在使用单体仓库。""写模型是事件溯源的，读模型投影到 Postgres 中。"
- **上下文之间的集成模式。** "订购和计费通过领域事件通信，而不是同步 HTTP。"
- **带有锁定效应的技术选择。** 数据库、消息总线、身份验证提供商、部署目标。不是每个库——只是那些需要花费一个季度才能替换的库。
- **边界和范围决策。** "客户数据由客户上下文拥有；其他上下文仅通过 ID 引用它。"明确的否定与肯定一样有价值。
- **故意偏离明显路径。** "我们使用手动 SQL 而不是 ORM，因为 X。"任何合理的读者会假设相反的事情。这些阻止下一个工程师"修复"故意的东西。
- **代码中不可见的约束。** "由于合规要求，我们不能使用 AWS。""响应时间必须在 200ms 以下，因为合作伙伴 API 合同。"
- **当拒绝不明显时的被拒绝替代方案。** 如果你考虑了 GraphQL 并出于微妙的原因选择了 REST，记录下来——否则有人会在六个月后再次建议 GraphQL。
