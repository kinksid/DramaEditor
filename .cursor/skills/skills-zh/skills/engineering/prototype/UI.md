# UI 原型

在单个路由上生成**几个截然不同的 UI 变体**，可通过浮动底部栏切换。用户在浏览器中翻转变体，选择一个（或从每个中窃取部分），然后丢弃其余的。

如果问题是关于逻辑/状态而不是看起来像什么——错误的分支。使用 [LOGIC.md](LOGIC.md)。

## 何时这是正确的形状

- "这个页面应该看起来像什么？"
- "我想在承诺之前看看这个仪表板的几个选项。"
- "为设置屏幕尝试不同的布局。"
- 任何用户否则会在脑海中三个模糊模型之间花费一天的时间。

## 两个子形状——强烈偏好子形状 A

当 UI 原型**与应用程序的其余部分相邻**时更容易判断——真实的标题、真实的侧边栏、真实的数据、真实的密度。单独的废弃路由是一个真空：每个变体在孤立时看起来都很好。只要有合理的现有页面来托管变体，就默认选择子形状 A。仅在原型确实没有附近的主页时才选择子形状 B。

### 子形状 A——对现有页面的调整（首选）

路由已经存在。变体在**同一路由**上渲染，由 `?variant=` URL 搜索参数控制。现有的数据获取、参数和身份验证都保持不变——只有渲染交换。这是默认值；除非有特定原因不选择，否则选择它。

如果原型是针对尚未有页面但*自然会存在于一个页面内*的东西（仪表板的新部分、设置屏幕上的新卡片、现有流程中的新步骤）——那仍然是子形状 A。将变体安装在宿主页面内。

### 子形状 B——新页面（最后手段）

仅在被原型化的东西确实没有现有页面可容纳时才使用此方法——例如全新的顶级表面，或无法嵌入任何合理位置的流程。

按照项目已经使用的任何路由约定创建**废弃路由**——不要发明新的顶级结构。命名它使其显然是原型（例如在路径或文件名中包含单词 `prototype`）。相同的 `?variant=` 模式。

在承诺子形状 B 之前，进行健全性检查：真的没有可以嵌入的现有页面吗？空路由隐藏了填充路由会暴露的设计问题。

在两个子形状中，浮动底部栏是相同的。

## 流程

### 1. 陈述问题并选择 N

默认为**3 个变体**。超过 5 个就不再是截然不同而开始成为噪音——在那里封顶。

用一行写下计划，在原型的位罝或文件顶部注释中：

> "设置页面的三个变体，通过 `?variant=` 切换，在现有的 `/settings` 路由上。"

无论用户是否在这里反驳，这都有效。

### 2. 生成截然不同的变体

起草每个变体。将每个保持到：

- 页面的目的和它可以访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
- 清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同的布局、不同的信息层次结构、不同的主要功能，而不仅仅是不同的颜色。三个稍微调整的卡片网格不是 UI 原型，它是壁纸。如果两个草案太相似，用明确的"不要使用卡片网格"指导重做一个。

### 3. 将它们连接在一起

在路由上创建一个单一的切换器组件：

```tsx
// 伪代码——适应项目的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形状 A（现有页面）：保持切换器上方的所有现有数据获取；只有渲染的子树每个变体更改。

对于子形状 B（新页面）：`/prototype/<name>` 下的废弃路由安装相同的切换器。

### 4. 构建浮动切换器

屏幕底部中心的一个小固定位置栏，有三部分：

- **左箭头**——循环到前一个变体（环绕）。
- **变体标签**——显示当前变体键，如果变体导出名称，也显示该名称。例如 `B — 侧边栏布局`。
- **右箭头**——向前循环（环绕）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架的路由器——Next 上的 `router.replace`、React Router 上的 `navigate` 等），以便变体是可共享和重新加载稳定的。
- 键盘：`←` 和 `→` 箭头键也循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时不要拦截箭头键。
- 视觉上与页面不同（例如高对比度药丸、微妙阴影），以便显然不是正在评估的设计的一部分。
- 在生产构建中隐藏——基于 `process.env.NODE_ENV !== 'production'` 或等效检查门控，以便意外的原型合并不会将栏运送给用户。

将切换器放在单个共享组件中，以便两个子形状都可以重用它们。将其放置在项目中共享 UI 所在的任何位置。

### 5. 交付

显示 URL（和 `?variant=` 键）。用户将在到达时翻转。有趣的反馈通常是**"我想要 B 的标题和 C 的侧边栏"**——那是他们真正想要的设计。

### 6. 捕获答案并清理

一旦变体获胜，写下哪个以及为什么（提交消息、ADR、issue 或原型旁边的 `NOTES.md`，如果在 AFK 运行且用户尚未响应）。然后：

- **子形状 A**——删除失败的变体和切换器；将获胜者折叠到现有页面中。
- **子形状 B**——将获胜变体提升为真实路由，删除废弃路由和切换器。

不要让变体组件或切换器闲逛。它们腐烂很快并混淆下一个读者。

## 反模式

- **仅在颜色或副本上不同的变体。** 那是调整，不是原型。真正的变体在结构上不同意。
- **在变体之间共享太多代码。** 共享 `<Header>` 是可以的；共享 `<Layout>` 违背了重点。每个变体应该可以自由地扔掉布局。
- **将变体连接到真实突变。** 只读原型是可以的。如果变体需要突变，将其指向存根——问题是"这应该看起来像什么"，而不是"后端是否工作"。
- **直接将原型提升到生产环境。** 变体代码是在原型约束下编写的（没有测试、最小错误处理）。当你折叠它时正确重写它。
