# 逻辑原型

一个小型交互式终端应用程序，让用户手动驱动状态模型。当问题涉及**业务逻辑、状态转换或数据结构**时使用——那种在纸上看起来合理但只有通过真实案例推动时才感觉不对劲的东西。

## 何时这是正确的形状

- "我不确定这个状态机是否处理了 X 然后 Y 的边缘情况。"
- "这个数据模型真的能让我表示……的情况吗？"
- "我想在编写之前感受一下 API 应该是什么样子。"
- 任何用户想要**按下按钮并观察状态变化**的事情。

如果问题是"这应该看起来像什么"——错误的分支。使用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在编写代码之前，写下你正在原型的状态模型和问题。一段话，写在原型的 README 或文件顶部的注释中。回答错误问题的逻辑原型纯粹是浪费——明确问题以便以后可以检查，无论用户现在是否在观看还是稍后返回。

### 2. 选择语言

使用宿主项目使用的语言。如果项目没有明显的运行时（例如文档仓库），询问。

匹配项目现有的工具约定——不要仅为了原型添加新的包管理器或运行时。

### 3. 将逻辑隔离在可移植模块中

将实际逻辑——回答问题的那部分——放在一个小而纯的接口后面，以后可以提取并放入真实的代码库中。周围的 TUI 是一次性的；逻辑模块不应该是一次性的。

正确的形状取决于问题：

- **纯 reducer**——`(state, action) => state`。当动作是离散事件且状态是单个值时很好。
- **状态机**——显式状态和转换。当"现在哪些动作甚至是合法的"是问题的一部分时很好。
- **一组小的纯函数**作用于普通数据类型。当没有隐式当前状态——只有转换时很好。
- **具有清晰方法表面的类或模块**，当逻辑真正拥有持续的内部状态时。

选择最适合所问问题的形状，*而不是*最容易连接到 TUI 的形状。保持纯净：没有 I/O，没有终端代码，没有用于控制流的 `console.log`。TUI 导入它并调用它；没有任何东西流向相反方向。

这使得原型在其自身生命周期之外有用。当问题得到回答后，经过验证的 reducer/机器/函数集可以提升为真实模块——TUI shell 被删除。

### 4. 构建暴露状态的最小 TUI

将其构建为**轻量级 TUI**——在每个 tick 上，清除屏幕（`console.clear()` / `print("\033[2J\033[H")` / 等效）并重新渲染整个帧。用户应该始终看到一个稳定的视图，而不是不断增长的滚动回退。

每个帧有两个部分，按此顺序：

1. **当前状态**，美观打印且对 diff 友好（每行一个字段，或格式化的 JSON）。对字段名或部分标题使用**粗体**，对不太重要的上下文（时间戳、ID、派生值）使用**暗淡**。原生 ANSI 转义码是可以的——`\x1b[1m` 粗体，`\x1b[2m` 暗淡，`\x1b[0m` 重置。除非项目中已经有样式库，否则不需要引入样式库。
2. **键盘快捷键**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 滴答时钟  [q] 退出`。对键使用粗体，对描述使用暗淡，或反之——只要清晰可读即可。

行为：

1. **初始化状态**——单个内存对象/结构体。启动时渲染第一帧。
2. **一次读取一个按键（或一行）**，分派到改变状态的处理器。
3. **每次操作后重新渲染**整个帧——不要追加，替换。
4. **循环直到退出。**

整个帧应该适合一个屏幕。

### 5. 使其可通过一个命令运行

向项目现有的任务运行器添加脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户应该运行 `pnpm run <prototype-name>` 或等效命令——永远不需要记住路径。

如果宿主项目没有任务运行器，只需将命令放在原型 README 的顶部。

### 6. 交付

给用户运行命令。他们会自己驱动它；有趣的时刻是当他们说"等等，那不应该可能"或"嗯，我假设 X 会不同"——这些是_想法_中的 bug，这正是重点。如果他们想要添加新动作，添加它们。原型会演变。

### 7. 捕获答案

当原型完成其工作后，问题的答案是唯一值得保留的东西。如果用户在身边，询问它教会了他们什么。如果不在，在原型的旁边留下一个 `NOTES.md`，以便在原型被删除之前可以填写答案（或者如果你观看了会话，由你填写）。

## 反模式

- **不要添加测试。** 需要测试的原型不再是原型。
- **不要将其连接到真实数据库。** 除非问题专门关于持久性，否则使用内存存储。
- **不要泛化。** 没有"如果我们以后想支持 X 怎么办"。原型回答一个问题。
- **不要将逻辑和 TUI 混在一起。** 如果 reducer/状态机引用 `console.log`、提示或终端转义码，它就不再是可移植的。保持 TUI 作为纯模块上的薄 shell。
- **不要将 TUI shell 部署到生产环境。** Shell 优化为从终端手动驱动。它后面的逻辑模块是值得保留的部分。
