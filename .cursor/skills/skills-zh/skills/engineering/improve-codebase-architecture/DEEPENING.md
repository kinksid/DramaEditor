# 深化

如何在给定依赖关系的情况下安全地深化一组浅模块。假设使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

在评估深化候选者时，对其依赖进行分类。类别决定了深化模块如何跨其接缝进行测试。

### 1. 进程内

纯计算、内存状态、无 I/O。始终可以深化——合并模块并直接通过新接口测试。不需要适配器。

### 2. 本地可替换

具有本地测试替身的依赖（PGLite 用于 Postgres，内存文件系统）。如果存在替身则可以深化。深化的模块在测试套件中使用运行的替身进行测试。接缝是内部的；模块的外部接口没有端口。

### 3. 远程但自有（端口和适配器）

跨越网络边界的自有服务（微服务、内部 API）。在接缝处定义**端口**（接口）。深层模块拥有逻辑；传输作为**适配器**注入。测试使用内存适配器。生产使用 HTTP/gRPC/队列适配器。

建议形式：*"在接缝处定义端口，为生产实现 HTTP 适配器并为测试实现内存适配器，这样即使部署在网络中，逻辑也位于一个深层模块中。"*

### 4. 真正的外部（模拟）

你无法控制的第三方服务（Stripe、Twilio 等）。深化的模块将外部依赖作为注入的端口；测试提供模拟适配器。

## 接纪律律

- **一个适配器意味着假设的接缝。两个适配器意味着真实的接缝。** 除非至少有两个适配器是合理的（通常是生产 + 测试），否则不要引入端口。单适配器接缝只是间接性。
- **内部接缝 vs 外部接缝。** 深层模块可以有内部接缝（对其实现私有，由其自己的测试使用）以及其接口处的外部接缝。不要因为测试使用它们就通过接口暴露内部接缝。

## 测试策略：替换，而不是分层

- 一旦在深化模块的接口处存在测试，浅模块上的旧单元测试就变成了浪费——删除它们。
- 在深化模块的接口处编写新测试。**接口是测试表面**。
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应该能够承受内部重构——它们描述行为，而不是实现。如果实现在变化时测试必须改变，那么它就是在接口之外进行测试。
