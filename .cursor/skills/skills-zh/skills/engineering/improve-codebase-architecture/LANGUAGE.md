# 语言

此技能提出的每个建议使用的共享词汇。精确使用这些术语——不要替换为"组件"、"服务"、"API"或"边界"。一致的语言是全部要点。

## 术语

**模块**
任何具有接口和实现的东西。故意与规模无关——同样适用于函数、类、包或跨层切片。
_避免_：单元、组件、服务。

**接口**
调用者正确使用模块必须知道的一切。包括类型签名，还包括不变量、顺序约束、错误模式、所需配置和性能特征。
_避免_：API、签名（太狭隘——这些仅指类型级表面）。

**实现**
模块内部的内容——其代码主体。与**适配器**不同：一个东西可以是带有大实现的小适配器（Postgres 仓库）或带有小实现的大适配器（内存假对象）。当接缝是主题时使用"适配器"；否则使用"实现"。

**深度**
接口处的杠杆——调用者（或测试）每单位必须学习的接口可以行使的行为量。当大量行为位于小接口后面时，模块是**深的**。当接口几乎与实现一样复杂时，模块是**浅的**。

**接缝** _（来自 Michael Feathers）_
你可以在不编辑该位置的情况下改变行为的地方。模块接口所在的*位置*。选择将接缝放在哪里是一个独立的设计决策，与后面的内容不同。
_避免_：边界（与 DDD 的有界上下文重载）。

**适配器**
在接缝处满足接口的具体事物。描述*角色*（它填充什么槽位），而不是实质（里面有什么）。

**杠杆**
调用者从深度中获得的东西。每单位必须学习的接口获得更多能力。一个实现在 N 个调用站点和 M 个测试中得到回报。

**局部性**
维护者从深度中获得的东西。更改、bug、知识和验证集中在一个地方，而不是分散在调用者中。修复一次，处处修复。

## 原则

- **深度是接口的属性，而不是实现的属性。** 深层模块可以在内部由小的、可模拟的、可互换的部分组成——它们只是不是接口的一部分。模块可以有**内部接缝**（对其实现私有，由其自己的测试使用）以及其接口处的**外部接缝**。
- **删除测试。** 想象删除模块。如果复杂性消失，模块没有隐藏任何东西（它是透传）。如果复杂性在 N 个调用者中重新出现，模块就在发挥作用。
- **接口是测试表面。** 调用者和测试跨越相同的接缝。如果你想测试*越过*接口，模块可能形状不对。
- **一个适配器意味着假设的接缝。两个适配器意味着真实的接缝。** 除非某些东西实际上跨越它变化，否则不要引入接缝。

## 关系

- **模块**恰好有一个**接口**（它向调用者和测试呈现的表面）。
- **深度**是**模块**的属性，针对其**接口**进行测量。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处并满足**接口**。
- **深度**为调用者产生**杠杆**，为维护者产生**局部性**。

## 拒绝的框架

- **深度作为实现行数与接口行数的比率**（Ousterhout）：奖励填充实现。我们改用深度作为杠杆。
- **"接口"作为 TypeScript `interface` 关键字或类的公共方法**：太狭隘——这里的接口包括调用者必须知道的每个事实。
- **"边界"**：与 DDD 的有界上下文重载。说**接缝**或**接口**。
