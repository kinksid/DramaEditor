# 接口设计

当用户想要为选定的深化候选者探索替代接口时，使用此并行子代理模式。基于"设计两次"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

在生成子代理之前，为选定的候选者编写面向用户的问题空间解释：

- 任何新接口需要满足的约束
- 它依赖的依赖项，以及它们属于哪个类别（参见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的说明性代码草图来具体化约束——不是提案，只是使约束具体化的方式

将此展示给用户，然后立即进行第 2 步。用户在子代理并行工作时阅读和思考。

### 2. 生成子代理

使用 Agent 工具并行生成 3+ 个子代理。每个必须为深化的模块产生**截然不同**的接口。

使用单独的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝后面的内容）提示每个子代理。简报独立于第 1 步中面向用户的问题空间解释。为每个代理提供不同的设计约束：

- 代理 1："最小化接口——最多目标 1-3 个入口点。最大化每个入口点的杠杆。"
- 代理 2："最大化灵活性——支持多种用例和扩展。"
- 代理 3："优化最常见的调用者——使默认情况变得简单。"
- 代理 4（如果适用）："围绕端口和适配器设计跨接缝依赖。"

在简报中包含 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，以便每个子代理使用与架构语言和项目领域语言一致的命名。

每个子代理输出：

1. 接口（类型、方法、参数——加上不变量、顺序、错误模式）
2. 显示调用者如何使用它的使用示例
3. 实现在接缝后面隐藏了什么
4. 依赖策略和适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——哪里杠杆高，哪里薄

### 3. 展示和比较

按顺序展示设计，以便用户可以吸收每一个设计，然后用散文比较它们。通过**深度**（接口处的杠杆）、**局部性**（变化集中的位置）和**接缝放置**进行对比。

比较后，给出你自己的建议：你认为哪种设计最强以及为什么。如果来自不同设计的元素可以很好地结合，提出混合方案。要有主见——用户想要强烈的观点，而不是菜单。
